# ACP Codex policy probe (PR #2210)

This local probe uses the **exact pinned `codex-cli 0.156.1` binary**. It starts an isolated app-server, an in-process MCP fixture, and a synthetic Responses API. It sends no request to a real model or Cloudflare. Output contains only versions, policy enums, method names, presence/absence fields, and outcomes. Canary assertions forbid URL and token values in the output.

Run with `CODEX_BIN` pointing to the pinned executable:

```sh
CODEX_BIN=/path/to/codex node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/codex PROBE_TOOL=command node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/codex PROBE_POLICY=granular node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/patched-codex PROBE_EXPLICIT_MCP=1 node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/patched-codex PROBE_EXPLICIT_MCP=0 node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/patched-codex PROBE_EXPLICIT_MCP=1 PROBE_TOOL=form node scripts/diagnostics/acp-codex-policy-probe.mjs
CODEX_BIN=/path/to/patched-codex PROBE_EXPLICIT_MCP=1 PROBE_DENIED_TOOL=1 node scripts/diagnostics/acp-codex-policy-probe.mjs
```

Observed on 2026-10-01:

| Policy                                 | Probe            | App-server result                                                                      | MCP fixture result                    |
| -------------------------------------- | ---------------- | -------------------------------------------------------------------------------------- | ------------------------------------- |
| `never`, danger-full-access            | ordinary command | no approval request; command output returned to model                                  | none                                  |
| `never`, danger-full-access            | URL MCP tool     | no elicitation request                                                                 | requested, then declined              |
| granular, only `mcp_elicitations=true` | URL MCP tool     | first a tool-approval **form**, then URL elicitation after the probe accepts that form | requested, then declined by the probe |

The granular policy preserves the tested ordinary command, but adds a tool-approval form ahead of this MCP URL tool. It is therefore **not** a drop-in replacement for SAM's current `never` policy while forms are disabled.

The current SAM configuration selects `INITIAL_AGENT_MODE=agent-full-access` in `packages/vm-agent/internal/acp/session_host_startup.go` and `approval_policy="never"` in `codex_config.go`. The pinned `codex-acp` maps that mode to a `turn/start` request with `approvalPolicy=never`. The real pinned Codex CLI read-back confirms `never` and `dangerFullAccess`. At [`codex-rs/codex-mcp/src/elicitation.rs` on `rust-v0.156.1`](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/codex-mcp/src/elicitation.rs), `elicitation_is_rejected_by_policy(Never)` returns true before `router.request_user_interaction`. This reproduces the live fixture's immediate `declined` outcome before a Cloudflare receipt.

## Exact-tag local patch under review

A pinned CLI backport plus a matching pinned adapter patch is the narrow option. The source diffs are [Codex CLI 0.156.1](patches/codex-cli-rust-v0.156.1-explicit-mcp.patch) and [Codex ACP 1.13.1](patches/codex-acp-v1.13.1-explicit-mcp.patch). Both `git apply --unidiff-zero --check` cleanly against their exact tags (`rust-v0.156.1` at `b412ff32c417f855c2b2d1581b77058eed87c84b`, `v1.13.1` at `b1b8490cd165c18626dc3fe83836cdacdef94cd3`). Their SHA-256 hashes are `8c81ca483469cdb967bf3205f625dd880e5801d9f1aef338a81a7f8149f045b4` and `689de4719a7f8fa37d6f9a218a4eee9cb3c022ee1e80240b60560b121d30abb9` respectively. These identify the patch source; no patched runtime has been distributed.

The adapter forwards only negotiated ACP `form`/`url` modes in a private app-server initialize extension. The generated TypeScript `InitializeCapabilities` accepts `extensions`, and `initialize_processor.rs` filters the extension into per-connection `ClientMcpExtensions`. A fresh or cold-resumed thread gets a distinct `McpRuntime` and `ElicitationRequestRouter`. Its opt-in defaults false; startup sets both booleans even when the extension is absent. A loaded thread's warm resume can only remove modes, including one disabled mode in a partial opt-in; `turn/start` carries the caller modes with its input; Core applies them only when that input starts a new turn, before its task runs. Steered or rejected input cannot grant modes to an active turn. A fork gets a separate router; non-root child sessions are forced false. Only root sessions with `ThreadSource::User` or the adapter's omitted (ordinary-user) source may enable it; explicit non-user sources are excluded. The pinned adapter omits `threadSource` on `thread/start`, which is why this differs from `full_access_form_input`'s `Some(User)` guard. Multiple app-server connections passed the local process probe; no rollout is authorized.

The CLI exception applies only to `AskForApproval::Never`, only to server-originated MCP form/URL requests of enabled modes, independent of the server permission profile after the MCP tool call has been admitted, and never when `codex_approval_kind` metadata marks a tool approval. All other policies retain the original rejection and `reviewer.review` path. The core Guardian reviewer keeps its call and defers its own Never-policy decline only for that same opted-in input; its explicit-input guard now also checks effective `AskForApproval::Never`, preserving the other-policy full-access/CUA empty-form shortcut; under Never other reviewers may still decline/cancel; an automatic reviewer acceptance is insufficient, and even an empty-schema confirmation form cannot auto-accept, so the request still awaits a human answer. `auto_deny`, cancellation, and responder-token checks remain in place. SAM continues to own the Cloudflare request/answer path; URL acceptance is distinct from completion.

Precisely, the patch removes the `elicitation_is_rejected_by_policy(Never)` early decline **only** when an opted-in, server-originated MCP form/URL request lacks `codex_approval_kind`; it does not require `mcp_permission_prompt_is_auto_approved` for that case. That predicate still guards the existing empty-form auto-accept and `openai/standard-form-input` shortcut, but it no longer gates this explicit input path. This is a behavior change for an already-admitted tool under a restricted permission profile: a human may now see its MCP input request. The patch does not change server existence, environment match, or `ToolFilter::allows` checks in `connection_manager.rs::call_tool`, nor the server/tool filtering used when publishing model tools. An explicit `disabled_tools=["request_remote_url"]` process probe with the extension enabled made no MCP tool invocation, emitted no app-server elicitation request, and received no implicit acceptance. A Rust regression in the exact-tag diff also verifies the disabled-tool filter rejects before a pending client connection can be awaited, even with the explicit elicitation router enabled. The elicitation path still requires a published per-server permission profile (`permission_profile_for_server` must return `Some`); the profile value is no longer a post-admission veto for this explicit input path.

The existing `openai/standard-form-input` client-only extension is relevant but different: `thread_manager.rs` enables it for a root `ThreadSource::User` after startup, and `elicitation.rs` then surfaces nonempty forms under an auto-approved server profile. It does not cover URL mode and bypasses the reviewer block for qualifying forms under policies beyond Never. Reusing that behavior for ACP URL would change reviewer semantics, so the new private mode-scoped extension is separate and is not advertised to MCP servers.

`explicit_mcp_mode_enabled_for` returns false for unsupported types and disabled modes. No global `on-request` or granular policy switch is proposed. Rollback is to remove both patch files from the build inputs and restore the unmodified exact npm pins (`@openai/codex@0.156.1`, `@agentclientprotocol/codex-acp@1.13.1`); the SAM branch currently still uses those stock packages.

The Claude failure is separate: `claude-agent-acp 0.81.2` receives SAM's ACP URL capability and attaches its `onElicitation` callback, but live Claude Code `2.1.281` did not advertise MCP URL elicitation to the fixture. The fixture's completion notifier failed before the adapter callback. A compatible Claude SDK/CLI fix or pin change is required; changing SAM's ACP advertisement alone cannot make that MCP initialize capability appear.

## Local verification and remaining gate

The [multi-client process probe](acp-codex-session-isolation-probe.mjs) passed eight cases: enabled new thread, disabled warm resume, disabled new thread, absent-extension warm resume, enabled reconnect/warm resume, enabled fork, active elicitation while another client resumes/steers/submits rejected input, and absent-capability cold process restart. The active request stayed pending until an explicit human-decline response. Only enabled turns emitted URL requests; the cold restarted thread with absent opt-in declined. The output excludes URL/token/header canaries. These cases use a synthetic model and local MCP fixture; Cloudflare delivery remains unproven.

Rust 1.95.0 was installed locally from `codex-rs/rust-toolchain.toml`; the build was bounded to two jobs on existing workspace disk. `cargo check -p codex-core -p codex-app-server` and the bounded `cargo build -p codex-cli --bin codex` passed. Targeted Core tests for Guardian policy/empty-form/cancellation and active-turn steer/reject ownership passed. The local patched executable reports the upstream version `codex-cli 0.156.1`; its SHA-256 is `6a870c44c4f9d5dfb45f565cf9be55031c7d1b29262a1c6c8ed3919134133d91`. This digest and the source patch hashes distinguish it from the stock pin. Adapter `npm run typecheck`, the focused initialize-forwarding test, and the full suite with `INITIAL_AGENT_MODE=agent` passed (744 tests; 26 skipped). The inherited SAM `agent-full-access` setting causes unrelated baseline mode-expectation failures in that upstream suite. The full `codex-mcp` suite passed (248 tests), including reviewer, cancellation, opt-out and empty-schema human-answer cases; the protocol extension-mode test and direct RMCP completion-capability/ID test passed.

The canary-safe real app-server probe gave these outcomes with the patched executable under `approvalPolicy=never` and `dangerFullAccess`: opt-in `form=true,url=true` produced `mcpServer/elicitation/request` in both URL and form modes and the fixture observed `requested → declined` only after the probe supplied a human-decline response; explicit false or absent opt-in produced no app-server request for either mode and the fixture declined; an ordinary command completed with no approval request. The stock executable also declined the URL request without an app-server request. The disposable fixture's existing auth/completion test passed after the optional local form tool was added. These observations prove the Codex CLI boundary, not the Cloudflare receipt. The adapter's existing completion-before/after-answer and cancellation tests passed in its full suite.

The [real Go client process test](../../packages/vm-agent/internal/acp/session_host_pinned_codex_process_test.go) uses the patched adapter, patched executable, synthetic Responses API, and a [local Cloudflare-compatible MCP fixture](acp-codex-mcp-fixture-server.mjs). Five cases passed: answer then completion, completion then answer, accepted answer without completion, human denial, and human cancellation. The real `sessionHostClient` writes through the local interaction recorder; the test asserts exact receipt, generation-bound answer, stale/replay rejection, one completion callback, and no duplicate completion. This proves the local receipt/answer contract, not live Cloudflare. Before the completion seam, the completion-before-answer case failed because pinned RMCP classified `notifications/elicitation/complete` as a custom notification and dropped it. The exact-pin backport now forwards that notification only when URL capability was advertised and its ID is valid; the adapter completes only its matching pending request. Its bounded (256-ID) process-lifetime tombstones reject reused IDs; an owner generation on each prompt and the process/session generation fence reject stale work. Child interactions retain the originating thread internally even when routed to the root session. The pending tracker clears on human decline/cancel, prompt abort, session close, process loss/restart, or next prompt. Accepted requests stay pending after the answer so early and late service completion remain distinct. `serverRequest/resolved` is emitted when an app-server request to its client is resolved; in the adapter it clears transient permission-call correlation and is ignored by the general event handler. Neither branch treats it as service completion.
